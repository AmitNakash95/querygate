The question we always get

“Why QueryGate and not a database firewall?”

A database firewall reads the SQL and decides — by pattern, or by whether it has seen that statement before — whether to let it through. QueryGate never receives SQL at all: the agent submits a typed JSON object with a fixed set of fields, and QueryGate writes the SQL itself.

Database firewall / DAM (database activity monitoring)

  • What it judges A SQL string it has to interpret — comments, encodings, dialect quirks and all.
  • The question it asks “Have I approved this statement, or flagged it?” One arm has to have seen the statement before; the other is an unbounded detection problem.
  • Facing a novel query An allow-list assumes traffic that repeats. An agent composes SQL it has never sent before on almost every request — so you block legitimate work, or you run permissive.
  • Decision granularity Allow, deny, alert or substitute a statement. A policy can name a table or a column — that part is table stakes.
  • Who asked The connection’s identity — usually a pooled app credential. App-user tracking, where it exists, is inferred, and lands in the log rather than in the decision.

QueryGate

  • What it judges A validated StructuredQuery object. No string in it is ever interpreted as SQL — a value is a bound parameter, a name is an escaped identifier — so a second statement or a comment is inert text, not syntax.
  • The question it asks “Is this shape allowed?” A closed question over a fixed set of typed fields.
  • Facing a novel query Novelty is irrelevant. A query never seen before is fine if its shape is in policy, and refused if it isn’t.
  • Decision granularity The query’s shape — joins, nesting depth, row caps, in-query masking, timeout — plus a column check that covers every reference, including one that appears only in a WHERE.
  • Who asked The human behind the agent, carried by delegation into the policy that gets applied, not only into the log.

And we are not telling you to remove yours. A firewall watches every path into the database — DBAs, applications, ETL, stolen credentials. QueryGate sits in none of those; it governs the one path a firewall can characterise least well: a non-deterministic agent writing new SQL on every request. Keep both.

The difference is not “blocks earlier.” A good firewall also stops a statement before it executes. The difference is what gets judged — a string you must out-guess, or a shape you defined.
